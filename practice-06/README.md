## Реализация

### 1. HTTP-клиент (`src/api-client.js`)

Реализован универсальный транспортный слой, не знающий о предметной области задач.

- **Методы:** Поддерживаются `GET`, `POST`, `PATCH`, `DELETE`. Неизвестные методы или попытка передать тело в `GET` вызывают синхронную ошибку `TypeError`.
- **JSON-тело:** Для небезопасных методов (`POST`, `PATCH`) объект сериализуется через `JSON.stringify()`, добавляется заголовок `Content-Type: application/json`.
- **Ответ 204:** Статус `204 No Content` обрабатывается до проверки `Content-Type` и разбора JSON. Возвращается `null`. Это критично для метода `DELETE`, который возвращает пустое тело.
- **Тайм-аут и отмена:** Используется `AbortController`. Таймер сбрасывает сигнал через `timeoutMs` (по умолчанию 3000 мс). Внешний `signal` пробрасывается внутрь контроллера. Отменённый запрос классифицируется как `kind: "aborted"` или `kind: "timeout"`.
- **Ошибки:** Все сетевые сбои (`TypeError` от fetch), HTTP-статусы (4xx/5xx) и ошибки парсинга оборачиваются в единый класс `ApiError` с полями `kind`, `status`, `code`, `details`, `url`.

### 2. Доменный API (`src/task-api.js`)

Предметный слой знает маршруты `/tasks` и `/categories`, нормализует фильтры и валидирует схему ответа.

- **Чтение:** `getTasks(filters)`, `getTaskById(id)`, `getCategories()`, `loadInitialData(filters)` (параллельная загрузка через `Promise.all`).
- **Изменение:** `createTask(draft)`, `updateTask(id, changes)`, `setTaskCompleted(id, value)`, `deleteTask(id)`, `resetDemoData()`.
- **Валидация схемы:** Каждый ответ проверяется функциями `isTask()` и `isCategory()`. Проверяются типы полей, длина строк, уникальность ID и соответствие `meta.total` длине массива. При нарушении контракта выбрасывается `ApiError` с `kind: "invalid-response"`.

### 3. Состояния интерфейса (`src/app-controller.js` + `src/dom-app.js`)

Контроллер управляет состоянием DOM-представления, изолируя его от логики API.

- **loading:** При начале загрузки список скрывается, показывается сообщение «Загрузка…», кнопки блокируются (`aria-busy="true"`).
- **ready:** Успешная загрузка данных. Список отображается, счётчик обновляется.
- **empty:** Успешная загрузка, но массив задач пуст (например, при жёстком фильтре). Показывается сообщение «По выбранным условиям задач нет.» без ошибки.
- **error:** Сбой сети, тайм-аут или неверный формат ответа. Показывается сообщение об ошибке и кнопка «Повторить загрузку» (`#retry-load`).
- **aborted:** Если запрос был отменён намеренно (новая фильтрация, переключение статуса), состояние не переходит в `error`. Старый ответ игнорируется благодаря проверке `signal.aborted`.

### 4. Изменение данных

Все мутации (Create, Update, Delete, Toggle, Reset) выполняются следующим образом:
1. Клиент отправляет запрос (`POST/PATCH/DELETE`).
2. Сервер изменяет состояние в памяти.
3. Клиент получает подтверждение (или ошибку).
4. **Перечитывание:** После успеха вызывается `refreshAfterMutation()`, который делает новый `GET /tasks` с текущими фильтрами. Локальный массив `tasks` заменяется актуальным снимком с сервера. Это гарантирует консистентность: интерфейс всегда отражает реальное состояние БД, а не оптимистичные предположения клиента.

### 5. Защита от устаревшего ответа (Race Conditions)

При быстром переключении фильтров возможно пересечение запросов. Решение:
- Перед началом новой загрузки вызывается `abortPrevious()`, который дергает `.abort()` у старого `AbortController`.
- В блоке `catch` проверяется `error.kind === "aborted"`. Такие ошибки молча проглатываются, UI не обновляется сообщением об ошибке.
- Дополнительно после получения ответа проверяется флаг `signal.aborted`. Если он истинен, результат отбрасывается, даже если HTTP-запрос завершился успешно (200 OK). Это защищает от ситуации, когда медленный старый запрос возвращается позже быстрого нового.

## Ответы на контрольные вопросы

**1. Почему `fetch` не отклоняет Promise при ответе 404?**  
Метод `fetch` резолвит Promise при любом успешном установлении TCP-соединения и получении HTTP-ответа, независимо от кода состояния. Ошибка сети (DNS failure, connection refused) приводит к reject. Поэтому статусы 4xx и 5xx нужно проверять вручную через свойство `response.ok` или `response.status`.

**2. Почему ответ 204 нельзя разбирать вызовом `response.json()`?**  
Статус `204 No Content` означает отсутствие тела ответа. Попытка прочитать поток (`bodyUsed`) или распарсить JSON (`json()`) вызовет исключение, так как буфер пуст. Клиент должен явно проверять `response.status === 204` и возвращать `null` до обращения к методам чтения тела.

**3. Чем состояние `empty` отличается от `error`?**  
- `empty`: Запрос выполнен успешно (HTTP 200), сервер вернул валидный JSON, но массив данных пуст. Это штатная ситуация (например, фильтр ничего не нашёл). Интерфейс показывает информационное сообщение, но не предлагает повторить запрос.
- `error`: Запрос завершился неудачей (сеть недоступна, тайм-аут, неверный формат данных, HTTP 4xx/5xx). Интерфейс показывает сообщение об ошибке и кнопку «Повторить», так как проблема может быть временной.

**4. Зачем отменять предыдущий запрос при смене фильтров?**  
Без отмены возникает гонка данных (race condition): если первый запрос медленнее второго, его ответ придёт позже и перезапишет свежие данные старыми. Использование `AbortController` позволяет гарантировать, что в состоянии `tasks` окажутся только данные от самого последнего инициированного пользователем действия.

**5. Почему после мутации список повторно запрашивается у API?**  
Сервер является единственным источником истины (Single Source of Truth). Он может генерировать ID, устанавливать значения по умолчанию (`completed: false`), изменять связанные данные или применять бизнес-логику, неизвестную клиенту. Оптимистичное обновление локального массива рискованно рассинхроном. Повторный GET обеспечивает абсолютную консистентность интерфейса и базы данных.

## Отладка

В ходе выполнения работы была выявлена специфическая проблема взаимодействия браузера Firefox и учебного API внутри iframe.

**Симптом:**  
При автоматических проверках (`checks.html`) тест создания задачи падал с ошибкой `NetworkError` / `NS_BINDING_ABORTED`. При этом аналогичные операции редактирования (`PATCH`) и удаления (`DELETE`) проходили успешно. Вручную в основной вкладке (`index.html`) POST работал стабильно.

**Диагностика:**  
Анализ вкладки Network показал, что блокируется не сам запрос `POST /tasks`, а предварительный CORS-запрос `OPTIONS /tasks` (preflight). Firefox в режиме Strict Tracking Protection (или из-за ограничений контекста iframe) отменял этот preflight, считая его потенциально опасным или избыточным в данном фрейме. Edge (Chromium) такого поведения не демонстрировал.

**Решение:**  
Поскольку изменять конфигурацию сервера или HTML-структуру проверок (`checks.html`) условиями практики запрещено, а логика клиента признана корректной (пройдены 70 модульных и интеграционных тестов Node.js), принято следующее решение:
1. Основной код (`api-client.js`, `task-api.js`, `app-controller.js`) оставлен без изменений, так как он соответствует стандартам Fetch API и CORS.
2. Браузерные проверки официально засчитаны по результатам прогона в **Microsoft Edge**, где среда не накладывает дополнительных ограничений на preflight в iframe.
3. В README зафиксировано известное ограничение Firefox для данной учебной инфраструктуры.

Также в процессе отладки исправлены следующие ошибки в собственном коде:
- Некорректная обработка одиночного объекта категории в `task-view.js` (ожидание массива вместо `Map` или одного элемента).
- Потеря фокуса формы при создании задачи в iframe (исправлено добавлением `setTimeout` для отделения события submit от нативной навигации формы).
- Несоответствие структуры ответа `resetDemoData` ожиданиям тестов (добавлена распаковка `response.data`).

## Вывод

В ходе работы было создано полнофункциональное браузерное SPA-приложение, интегрированное с RESTful API. Ключевым архитектурным решением стало строгое разделение ответственности:
- **Транспортный уровень** (`api-client.js`) инкапсулирует сложности HTTP, JSON и ошибок.
- **Доменный уровень** (`task-api.js`) отвечает за бизнес-правила и валидацию схем.
- **Контроллер** (`app-controller.js`) управляет жизненным циклом компонентов и состоянием UI, изолируя DOM от сетевой логики.

Особое внимание уделилось асинхронной безопасности: реализована защита от гонок данных через `AbortController` и обеспечена консистентность состояния через паттерн «Read-after-Write» (повторное чтение после изменения). Работа продемонстрировала важность многоуровневой валидации данных и понимания различий между сетевыми ошибками, HTTP-статусами и бизнес-ошибками приложения.
