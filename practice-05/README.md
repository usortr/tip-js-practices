## Организация кода
| Файл | Ответственность |
| --- | --- |
| `api/server.mjs` | Готовый учебный HTTP-сервер. Хранит данные в памяти, обрабатывает маршруты, CORS и имитирует ошибки/задержки. |
| `src/api-client.js` | Универсальный транспортный уровень. Формирует URL, выполняет `fetch`, обрабатывает таймауты (`AbortController`) и преобразует любые ошибки в единый класс `ApiError`. |
| `src/task-api.js` | Предметный уровень. Знает маршруты (`/tasks`, `/categories`), нормализует фильтры, валидирует схему возвращаемых данных и предоставляет удобные методы. |
| `src/variant.js` | Конфигурация индивидуального варианта (номер и фильтры). Не содержит логики. |
| `src/main.js` | Точка входа. Инициализирует клиенты, выполняет контрольный сценарий и выводит форматированный результат в терминал. |

**Почему `fetchFn` передаётся аргументом?**  
Для внедрения зависимостей (Dependency Injection). Это позволяет тестировать клиент с помощью поддельной функции (mock) без реальных сетевых запросов.

**Почему HTTP-ошибки проверяются отдельно от сетевых?**  
`fetch` считает ошибкой (reject) только сбой сети (`TypeError`). HTTP-статусы 4xx и 5xx считаются "успешным" завершением запроса с точки зрения протокола, поэтому их нужно проверять вручную через `response.ok`.

**Почему JSON после разбора всё равно проверяется по контракту?**  
Успешный `JSON.parse` гарантирует только синтаксическую корректность. Данные могут быть повреждены, иметь неверную структуру или не соответствовать бизнес-логике, что вызовет падение приложения при попытке их использовать.

## Реализация общего клиента
| Требование | Как реализовано | Проверка |
| --- | --- | --- |
| Нормализация `baseUrl` | Добавляется завершающий `/`, если его нет. Проверяется через `new URL()`. | Тесты на некорректные URL (протокол, query). |
| Кодирование query-параметров | Используется встроенный `URLSearchParams`, который автоматически кодирует спецсимволы. | Тест на `q: "API & ошибки"`. |
| Заголовок `Accept` | Явно передаётся `headers: { "Accept": "application/json" }`. | Проверка в mock-вызовах `fetchFn`. |
| Проверка `response.ok` | Если `!response.ok`, выбрасывается `ApiError` с `kind: "http"`. | Тесты на 404 и 503 ошибки. |
| Проверка `Content-Type` | Проверяется наличие `application/json` в заголовке. Иначе `kind: "invalid-response"`. | Тест с `text/plain`. |
| Разбор JSON | Вызывается `await response.json()` внутри `try...catch`. | Тест с повреждённым JSON (`{broken`). |
| Ограничение времени | Используется `setTimeout` + `AbortController`. | Тест с задержкой, превышающей `timeoutMs`. |
| Внешняя отмена | `externalSignal.addEventListener("abort", ...)` передаёт отмену в контроллер. | Тест с ручным `controller.abort()`. |

## Отладка
**Точки останова:**
1. До `fetch`: проверка сформированного `url` и `options.signal`.
2. После получения `Response`: проверка `response.status`, `response.ok`, `response.headers.get('content-type')`.
3. Перед `response.json()`: убеждаемся, что статус 2xx и тип контента верный.
4. В `catch`: анализ `error.name` (для AbortError) и типа ошибки (`TypeError` vs `ApiError`).

**Пример успешного запроса:** URL=`.../tasks/25`, status=`200`, ok=`true`, payload=`{ data: {...} }`.
**Пример ошибочного запроса:** URL=`.../tasks/999`, status=`404`, ok=`false`, итоговый `ApiError` содержит `kind: "http"`, `code: "TASK_NOT_FOUND"`.

## Вывод
В ходе работы был создан надёжный, переиспользуемый HTTP-клиент, разделённый на транспортный и предметный слои. Освоены современные подходы к асинхронности: `async/await` для читаемости, `Promise.all` для параллелизма и `AbortController` для управления временем жизни запросов. 

Главный инсайт: **валидация должна быть многоуровневой**. Ожидание Promise завершается успешно даже при HTTP 404, поэтому статус нужно проверять вручную. Сетевая ошибка (`TypeError`) отличается от HTTP-ошибки (статус 4xx/5xx). Даже если JSON успешно разобран, его структура всё равно должна быть проверена по контракту, чтобы защитить приложение от некорректных данных.
